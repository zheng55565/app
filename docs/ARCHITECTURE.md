# AI公益工作台架构边界

## 1. 地址与模型来源

App只访问业务后台，例如 `https://api.example.com`。业务后台分别调用：

- New API管理接口：查找Linux.do对应账号、发放广告额度、查询真实余额。
- New API的OpenAI兼容接口：获取模型、流式对话和生图。
- 广告平台服务器接口：只接收经过平台签名验证的奖励回调。

App不接收任意Base URL，也不保存New API管理员令牌。要增加OpenAI、Claude、Gemini或其他中转渠道，应优先在New API后台配置渠道和模型映射。这样App不需要发版，所有模型仍使用同一个本站额度账本。

外部中转站是另一套独立账本。即使以后允许用户填写外部Key，也只能消费外部站余额，不能消费本站广告额度。若实现该能力，地址必须来自服务端白名单；不能把客户端提交的URL直接交给Node请求。

## 2. 额度闭环

```text
Linux.do登录 -> 创建一次性广告任务 -> 广告SDK播放
                                      |
广告平台服务器签名回调 ----------------+
        |
账号/设备/IP每日上限 + 交易号幂等
        |
reward_orders本地订单 -> New API账号增加quota
        |
网站API / App工作台 / App生图消费同一quota
```

客户端“播放完成”事件不发额度。额度不可提现、不可转赠，后续游戏只能向服务端提交操作，由服务端在独立游戏账本中原子结算，客户端不能直接修改余额。

## 3. 当前四个页面

- 工作台：本站模型列表、流式对话、会话内上下文。
- 生图：生图模型、提示词、尺寸和图片结果。
- 额度：真实New API余额、今日广告次数、看广告入口和现有小游戏入口。
- 我的：账号状态、按账号隔离保存的本站New API Key、退出登录。

当前工作台是AI对话MVP，不等同于完整Claude Code或Codex。完整代码代理至少还需要任务队列、项目文件存储、隔离执行容器、命令审批、资源配额、任务取消和审计日志。

## 4. Codex式任务服务拆分

任意代码和命令不得在现有API进程内执行。后续应新增独立Worker：

```text
App/Web -> API网关 -> 任务队列 -> 沙箱Worker -> 模型/New API
                    |             |
                    |             +-> 临时项目卷、CPU/内存/时长限制
                    +-> PostgreSQL任务状态、对象存储产物、审计日志
```

每个任务使用短生命周期容器或等价沙箱，默认禁止访问宿主机文件、Docker socket和内网管理端口。任务取消时只终止对应Worker，不影响登录、广告和其他用户请求。

## 5. 并发与可用性

- Node对AI响应全程流式转发，不缓存完整回答或图片。
- PostgreSQL租约统一限制全站和单用户并发，支持多个Node副本。
- Nginx对登录、广告和AI分别限速，AI关闭代理缓冲。
- 生产至少两个Node副本；New API和PostgreSQL分别做健康检查、备份和告警。
- 图片生成、文档生成和代码执行应进入异步任务队列，避免长任务占满HTTP进程。

## 6. 上线前不可省略

- 使用真实广告平台的官方服务端签名校验替换通用HMAC示例。
- 接入Play Integrity、App Attest或渠道等价证明；安装ID只能拦截普通多开。
- 执行全部数据库迁移，并做广告并发回调和额度对账测试。
- 从公网确认Node内部端口、New API管理端口、PostgreSQL和Redis不可访问。
- 对 `pending`、`crediting` 奖励订单建立告警和人工对账流程。
